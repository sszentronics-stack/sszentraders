# Phase 14 Completion Report — Reviews, Returns & Customer Service

## Implementation summary

Phase 14 completes post-purchase trust workflows on top of every prior phase's already-built machinery: verified-purchase product reviews with moderation, a full customer return-request → admin approve/reject → courier pickup → received/inspection → refund-or-replacement lifecycle, and the financial refund flow (local accounting event, Easypaisa refund, LedGix ERP credit note). Nothing here re-implements what a prior phase already built — it wires new domain logic on top of Phase 7's accounting service, Phase 8's ERP sync worker, Phase 10's Easypaisa refund path, and Phase 11's Leopards return-pickup booking, exactly as those phases' "next-phase readiness" sections anticipated.

Delivered:
- **Verified-purchase reviews** (`backend/lib/reviews`, `backend/services/reviews/reviews.service.ts`): a customer may review a purchased line item only once its order is `delivered` and only once — enforced both by a pure eligibility decision (`evaluateReviewEligibility`) and a database-level `UNIQUE(order_item_id)` constraint on the new `product_reviews` table. Star rating (1–5), title, body, optional photo evidence (signed-upload-URL pattern reused from Phase 3's product images), and a `pending`/`published`/`rejected` moderation state. Public reads of published reviews go straight through RLS (no Edge Function round-trip needed); every write goes through the new `reviews` Edge Function, which re-verifies eligibility server-side.
- **Return-policy eligibility engine** (`backend/lib/returns`): a real, configurable, server-side decision — delivered order state, the real shipment `delivered_at` date (never guessed from `order_status` alone), a configurable return window (`RETURN_POLICY.windowDays`), per-item remaining-quantity accounting across all prior non-rejected requests, a structured reason-code vocabulary, and evidence-required-for-some-reasons enforcement. The frontend never asserts eligibility, quantity, or amount — it only reflects what this engine already decided.
- **Customer return request flow** (`backend/services/reviews/returns.service.ts`): eligible-item listing, evidence upload (private `return-evidence` bucket, signed URLs), request creation, own-return listing/detail with a full status timeline (`return_events`).
- **Admin return review/approve/reject** (same file): a real state machine (`requested → under_review → approved/rejected → pickup_requested/received → refunded/replaced → closed`) reusing the same "pure transition table + assert" pattern `backend/lib/status` already established for orders, extended here for `return_status`. Every transition is audited and appended to `return_events`.
- **Courier handoff**: `approveReturn()` immediately attempts Phase 11's already-built `bookReturnPickup()` — never re-implemented, never fabricates a tracking number. A courier failure (today: always `IntegrationNotConfiguredError`, no real Leopards credentials exist) does not roll back the approval; it's recorded and the pickup can be retried later via the existing `shipments` Edge Function.
- **Received/inspection outcome → refund or replacement** (`recordInspectionOutcome`): the return must be `received` first; a refund amount is required, server-capped against the return's own computed estimate (never an arbitrary admin-typed number beyond what was actually eligible), and the return moves to `refunded`/`replaced`.
- **Financial refund flow** (`backend/services/reviews/refund.service.ts`): decides Easypaisa vs. manual/COD from the order's actual payment provider/status, records the local refund event via **Phase 7's `accounting.service.ts` only** (no second local-financial-event writer), attempts an Easypaisa refund via the already-built `EasypaisaProvider`/`refundEasypaisaPayment` when applicable, and drives Phase 8's real `attemptErpSync()` for the LedGix credit note (`refund` already maps to `credit_note` in Phase 8's `mapFinancialEventToErpAction` — no new ERP mapping logic was needed). Every real provider call still throws `IntegrationNotConfiguredError` today; nothing here fabricates a refund reference or ERP document number.
- **No inventory touched**: for a `replacement` resolution, this phase deliberately does not adjust any inventory-shaped table. `backend/services/inventory`/`backend/lib/inventory` were still just README placeholders (Phase 9 not yet merged) at the time this phase was built, so per the explicit instruction, inventory is left entirely alone — see "Known limitations" below.

## Architecture and key decisions

- **`backend/lib/reviews` / `backend/lib/returns` mirror the established `backend/lib/<area>` vs `backend/services/<area>` split** (pure, zero-I/O, unit-tested domain logic vs. Supabase orchestration) that every prior phase uses — same shape as Phase 7's `accounting`/Phase 8's `erp`. Return status transitions were added to the **existing** `backend/lib/status` module (alongside `ORDER_TRANSITIONS`) rather than a new file, since that module's own doc comment already declares itself the single source of truth for "status vocabularies + transition validation" across the whole schema.
- **Reviews and returns writes are Edge-Function-only, matching the `returns`/`return_items` table's own Phase 1 RLS shape** (`*_self_read` + `*_admin_all`, no authenticated insert/update policy). A customer's eligibility (verified delivered purchase, remaining quantity, review-once) requires cross-table joins RLS alone cannot safely express without duplicating this phase's own decision logic into SQL, so — like `orders`/`payments`/`shipments` before it — every write goes through a service-role Edge Function that re-derives and re-checks eligibility itself.
- **One return can only have one resolution (refund XOR replacement), decided at the return level, not per return_item.** The spec's "received/inspection outcome → replacement or refund decision" reads as a single decision per return, and Phase 1's `returns.refund_amount` (a single column) already implied this shape. A future phase wanting mixed per-item outcomes within one return would need a schema change; documented under "Known limitations."
- **Return refund amount is a two-stage number, both server-computed**: at request time, `returns.refund_amount`/`return_items.refund_amount` are set to the *maximum refundable estimate* (`unit_price × requested quantity`, from the order's own snapshotted price — never a client-supplied amount). At inspection time, `recordInspectionOutcome()` requires an explicit admin-decided amount and **caps it** to that estimate — an admin can refund less (e.g. a partial/restocking-fee refund) but never more than what was actually eligible. This is the concrete "refund amount... determined server-side" enforcement the phase's security requirement asks for.
- **"Decide the outcome" and "move money" are two separate, independently-testable functions** — `returns.service.ts`'s `recordInspectionOutcome()` only transitions the return and records the local "goods physically returned" accounting event (for *both* resolutions — a replacement still means stock came back); `refund.service.ts`'s `processReturnRefund()` (called by the Edge Function right after, only when `resolution === 'refund'`) does the refund-specific financial work. This mirrors Phase 8's own "sync-state primitives are a separate concern from the domain event" split.
- **Courier pickup booking is invoked directly from `approveReturn()`, not left as a separate manual admin step**, because Phase 11's own "next-phase readiness" section explicitly said Phase 14 "can call `bookReturnPickup()` the moment a return reaches `approved`." A courier failure never blocks or rolls back the approval — same "never let an expected not-configured integration failure block the core operational action" pattern Phase 7's best-effort `erp_sync_jobs` insert already established.
- **The LedGix credit note for a refund reuses Phase 8's real sync worker (`attemptErpSync`) unchanged** rather than calling `ErpProvider.recordCreditNote()` directly — `refund` was already wired to `credit_note` by Phase 8's `mapFinancialEventToErpAction`, so this phase adds zero new ERP-mapping code, exactly the reuse the task brief asked for.
- **A new, small in-memory Supabase fake** (`backend/services/reviews/testUtils.ts`) extends the shape Phase 11's `backend/services/delivery/leopards/testUtils.ts` established (select/insert/update, eq/neq/in/not, order/limit, maybeSingle/single) with multi-row insert (needed for bulk evidence-row insertion) and a `count`/`head` select (needed for the per-review image cap) plus a minimal fake `.storage.from(bucket).createSignedUploadUrl()`. Test-only, not exported outside the test suite, following the same "not a general mock" philosophy.
- **Migration numbering**: `0021_reviews_and_returns_workflow.sql` was the next free number after `0020` at the time this phase was written (Phase 9's inventory migration had not landed on `main` yet in this session). If Phase 9 also lands a `0021` from its own parallel session, both files are additive and touch disjoint tables (this migration never touches `inventory_cache`/`products` stock columns), so applying either ordering is safe — the same resolution Phase 8 documented for the earlier `0019` collision. This is called out in the migration's own header comment and in `supabase/migrations/README.md`.

## Database/schema changes

One new migration: `supabase/migrations/0021_reviews_and_returns_workflow.sql`.

- **New**: `review_status` enum (`pending`/`published`/`rejected`); `product_reviews` (rating, title, body, status, moderation fields, `UNIQUE(order_item_id)` as the verified-purchase/no-duplicate-abuse guard); `product_review_images`; `return_item_evidence` (photo evidence for a return line item).
- **Extends `returns`** (Phase 1, `0009_returns.sql`, unchanged otherwise): `resolution` (`refund`/`replacement`), `inspection_outcome`, `inspection_notes`, `refund_method` (`easypaisa`/`manual`), `refund_payment_id` (FK to `payments`), `ledgix_credit_note_id`/`ledgix_credit_note_number`.
- **Extends `return_items`**: `reason_code`, a fixed structured vocabulary (`damaged_in_transit`/`wrong_item_received`/`not_as_described`/`defective_quality`/`changed_mind`/`size_fit_issue`/`other`), check-constrained.
- **Two new storage buckets**: `review-images` (public read — customer evidence on a published review is customer-facing) and `return-evidence` (**private** — no public-read policy at all; read only via a service-role-issued signed URL, since this is customer-specific dispute evidence, not storefront content).
- **RLS**: `product_reviews`/`product_review_images` get public-read-of-published + self-read + admin-all policies (no authenticated insert/update — writes are Edge-Function-only, matching `returns`' own existing shape). `return_item_evidence` gets self-read (row metadata only, not the storage bytes) + admin-all. No RLS changes to the pre-existing `returns`/`return_items`/`return_events` policies — their existing `*_self_read`/`*_admin_all` shape was already sufficient for the new columns.
- No changes to `orders`, `order_items`, `payments`, `shipments`, `local_financial_transactions`, `erp_sync_jobs`, or any inventory-shaped table.

## Security and permissions

- **Every review/return mutation is server-side authorized.** `createReview`/`createReturnRequest`/evidence-upload-URL issuance all re-derive ownership from `profiles → customers → orders/order_items`, never trust a client-asserted order/customer id, and use the same "never distinguish not-yours from doesn't-exist" `NotFoundError` pattern `orders.service.ts`'s `getOrderForCaller()` established.
- **Eligibility, quantity, and refund amount are 100% server-decided.** The frontend sends only a reason code, quantity, and optional notes/evidence paths; `evaluateReturnEligibility()`/`evaluateReviewEligibility()` (pure, unit-tested) are the sole source of truth, and `recordInspectionOutcome()` hard-caps any admin-submitted refund amount to the server-computed maximum.
- **Every admin action is audited** via `backend/lib/audit`'s `writeAuditLog()`: `return.moved_under_review`, `return.approved`, `return.rejected`, `return.received`, `return.inspection_outcome_recorded`, `return.closed`, `return.pickup_booking_attempted`, `return.refund_processed`, `review.moderated` — each with non-secret, minimal metadata (status transitions, outcome flags, amounts), never a raw provider payload.
- **`return-evidence` is a private bucket** — no public-read storage policy exists at all; access is only ever via a service-role-issued signed upload/read URL, so a customer's dispute photos are never exposed to the public internet the way `product-images`/`review-images` intentionally are.
- **Every admin-only route requires `requireAdmin()`** (JWT-verify + `profiles.is_admin`); every caller-only route requires `requireCallerProfile()`. No route trusts a client-asserted `isAdmin`/`profileId` field in the request body.
- **No new secrets were introduced** — the refund flow reuses the already-configured `EASYPAISA_*`/`LEDGIX_*` Edge Function secrets (still blank in this environment) via the existing `_shared/config.ts` getters.

## External integration impact

**No live Easypaisa, LedGix, or Leopards call was made or invented.** `refund.service.ts`'s `processReturnRefund()` calls `refundEasypaisaPayment` (Phase 10) and `attemptErpSync` (Phase 8) exactly as those phases built them — every real provider method still throws `IntegrationNotConfiguredError`, verified by this phase's own tests (`easypaisaError`/`erpSyncOutcome !== 'succeeded'`/`ledgixCreditNoteId === null` in the not-configured case). `returns.service.ts`'s `approveReturn()` calls Phase 11's real `bookReturnPickup()` unchanged — same fail-safely behavior, verified by test. ## Known limitations/deferred items

- **One resolution per return, not per return_item.** A return spanning multiple line items resolves as a single refund-or-replacement decision (matching Phase 1's single `returns.refund_amount` column). Splitting resolutions per item within one return would need a schema change beyond this phase's scope.
- **Evidence storage paths are trusted as asserted by the customer at request-creation time** — `createReturnRequest()` does not verify a given `evidenceStoragePaths` entry actually exists as an uploaded object in the bucket (it only validates the *shape*/count via Zod). A fabricated path is self-evident to an admin reviewing the return (a broken image) rather than exploitable — the actual upload path itself is properly access-controlled (signed URL, ownership-checked, private bucket).
- **No admin UI** was built — Phase 12's job, per the same pattern every prior phase has followed. The full admin service/Edge Function layer (review/approve/reject/receive/inspection-outcome, review moderation, listing/filtering) is real, complete, and audited, ready for Phase 12 to build a page against without touching this phase's files again.
- **Return-policy configuration is a code constant** (`RETURN_POLICY.windowDays = 7`), not an admin-editable value — no admin-configurable-policy system exists yet in this codebase. Changing the window today means a code change, not a database row.
- **No package weight/dimensions or cutoff-window logic for the return pickup booking itself** — same documented gap Phase 11 already flagged for outbound bookings; this phase doesn't add anything new here, it only calls the existing `bookReturnPickup()`.
- **Inventory is deliberately untouched.** Phase 9 (ERP-Controlled Inventory & Availability Synchronization) had not landed on `main` at the time this phase was implemented (`backend/services/inventory`/`backend/lib/inventory` were still README-only placeholders). Per the explicit instruction, a `replacement` resolution does **not** adjust any inventory-shaped table — there is no local stock-adjustment path anywhere in this phase's code. Once Phase 9 lands, a follow-up pass should decide how (if at all) Aura's inventory *cache* refreshes after a replacement/return is confirmed by ERP — this phase intentionally leaves that decision to Phase 9's owner rather than inventing a local one.
- **No live-database, live-provider, or live Edge Function router test** — same documented limitation as every prior phase (no live Supabase project or provider sandbox in this environment). All decision/eligibility/state-machine/refund-orchestration logic is fully unit tested against an in-memory fake and the real (not-configured) provider classes.
- **Guest (non-authenticated) returns/reviews are out of scope**, same as Phase 8/10's guest-order-ERP-sync limitation — both flows require `requireCallerProfile()` (a resolvable `customers` row via `profile_id`), which anonymous-auth guest checkout already provides per Phase 5/6, but a guest who loses their browser session has no path back to their return/review the way `orders.service.ts`'s `lookupGuestOrder()` provides for orders. A future pass could add an equivalent order-number+email lookup for returns if needed.
